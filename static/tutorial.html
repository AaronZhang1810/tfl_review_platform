1. What the app does

You upload one or more TLF output PDFs (e.g. an Investigator Brochure table package). The app indexes every table from the PDF bookmarks, lets you page through each one, record a review status, leave comments, and run an AI review that reads each table and judges it against a configurable checklist. If you upload two editions (e.g. this year vs last year), it also compares them.

How model assistance is used. In normal source mode, a configured Claude model proposes review candidates, guided by an editable checklist (see §8): it reads each table, extracts the numbers, and decides what looks wrong. Only three structural checks are plain deterministic code — blank pages, an output missing versus last year, and a numbering gap. Two guards keep the AI honest: an extraction self-check re-reads any number whose count and percent don’t line up before judging, and a verify pass has Python re-do the arithmetic the AI itself cites and drops any finding whose own numbers don’t actually contradict. Every finding carries a risk tier and is a candidate a human confirms, not a final verdict.

2. Starting the app

The app runs locally in your browser and requires Python 3.11 or 3.12.

From the repository root, run ./run_synthetic_demo.sh on macOS/Linux or RUN_SYNTHETIC_DEMO.bat on Windows. The launcher creates an isolated fictional project and opens the browser when ready. Leave the terminal open while you work — closing it stops the server.

The synthetic demo is normally at http://127.0.0.1:8765. To stop it, return to the terminal and press Ctrl+C.

The app tells you when it's working. A thin animated bar across the very top of the window appears whenever the app is busy — opening a project, running an action, importing or exporting. A slow step (a large Excel import can take a while) therefore never looks frozen: as long as the bar is moving, the app is still working.
The synthetic demo never calls an external model. Its findings are pre-seeded and model behavior is simulated, even if the launching shell contains an API key. In normal source mode, model-backed AI Review and chat require an ANTHROPIC_API_KEY; browsing PDFs, statuses, comments, and exports do not.

3. Creating and sharing projects

The one-click demo already contains a fictional project. Explore that generated project without uploading a document or enabling an external model.

To create your own, fill the form on the left of the home page:

  • Compound / Study / Project name — free text to identify the delivery.
  • Delivery TLF PDF(s) — one or more PDFs. To enable year-over-year comparison, upload both editions (the app detects each edition year from the cover/header).
  • SAP / Protocol (optional) — reference documents that power SAP-aware answers in chat.

Click Create project. Existing projects appear on the right; click one to open it, or use Delete to remove it. You may import/export projects as .zip files.

4. Overview dashboard 📊

Opening a project lands you on Overview — an at-a-glance summary of where the review stands, so you don't have to scan the TOC to know what is left. It is computed live from your current data, and (like the rest of the app) needs no API key.

  • KPI cards — the four headline numbers: outputs approved, AI findings still open, findings flagged for attention, and comment threads resolved.
  • Review-status donut — every output split across Not Reviewed / In Progress / Approved / Needs Revision.
  • Findings panel — the open-vs-addressed split, a severity breakdown, and separate tiles for findings marked new or may be resolved.
  • Comments meter — resolved versus open threads.
  • Last AI run — a chip shows when the review last ran (or “Not run yet”).

Click a card or panel header to jump straight to the tab behind it (TOC, AI Review, Comments). A brand-new project with no outputs, findings or comments still renders cleanly, with friendly empty states instead of blank panels.

5. TOC tab 📋

A searchable table of every output: Type, Number, Output, Title, Pages, Status. Type in the search box to filter by label or title. Click any Output link (e.g. Table 2.2.1) to open it in the TLF workspace.

6. TLF review workspace 📑

Three columns:

  • Left — bookmark list: every output; click to jump. The current one is highlighted.
  • Centre — the PDF: just the pages for that output.
    • ‹ Prev / Next › move between outputs.
    • ◀ / ▶ move between pages within the output. The label shows “Page X / N (doc p.NNN)” so you always know the real page in the source PDF.
    • − / Fit / + zoom. The page fits the column width by default; click + to enlarge dense tables, Fit to reset. Rendering is high-resolution, so zooming in keeps text sharp.
    • Check TOC jumps back to this output’s row in the TOC tab.
  • Right — sidebar:
    • Review status: Not Reviewed → In Progress → Approved / Needs Revision. Adding a comment or posting an AI finding auto-moves it to In Progress.
    • Comments: add a title (optional) + comment; delete any comment.
    • AI findings: the findings for this specific output (after a run).
    • Ask about this output: a mini chat scoped to this table.

7. AI Review tab 🤖

If this project came pre-reviewed, its findings are already here — you can read them with no API key. A key is only needed to run or re-run the review, or to use chat.

Run: click ▶ Run AI review. A progress bar shows which output is being analysed. Findings appear grouped and colour-coded by risk. You can also pick the Model and reasoning Effort; an estimated time updates as you change them.
Fresh re-run: ignores the cache and re-reads and re-judges every output from scratch (slower). Use it if you suspect a stale AI reading.
Import Excel: load findings from a structured .xlsx — the reverse of Export. Columns are matched by header name (Output, Risk, Finding, optional Page/Section), so you can export, edit in Excel, and re-import, or author findings offline. Imported findings are added alongside the AI ones (they aren’t wiped by a later AI run); a row whose Output label isn’t in this project is still imported but not tied to a table.
Runs are continuable. Each table’s findings are saved the moment it’s judged, so if the app or laptop shuts down mid-run, nothing already done is lost. Just click ▶ Run AI review again — it skips the tables it already finished and does only what’s left. For the same reason a normal re-run is fast: unchanged tables (same model, effort and checklist) are reused rather than re-judged. Fresh re-run is the way to force a full re-judge.
Caching & cost in normal source mode. The first model-backed run is the slow one (the configured model reads and judges each output). Extractions are cached by content, so a normal re-run is fast and only re-reads outputs whose content changed. Every table in the current edition is analysed (listings and figures are not); the tab shows how many outputs were analysed and how many skipped. If the API can’t be reached, the run aborts loudly and says so — it will not quietly report “0 findings”.
Coverage — read this if you see an amber banner. A very long table is read page by page, and there is a safety cap on how many pages one table may use. If a table hits that cap, the pages past it are never sent to the AI, so no finding can exist for them — “0 findings” on such a table does not mean it is clean. The run line shows read N/M pages, and an amber banner lists any table that was only partially read. The default cap is high enough that normal deliveries are read in full; if you do hit it, set TLF_MAX_SLICES higher (or 0 for no limit) and re-run.

Speed

Tables are analysed concurrently, and the page-by-page reading is done by a smaller, faster model while the judging uses the model you picked. Three environment variables tune this if you ever need to:

VariableDefaultEffect
TLF_MAX_INFLIGHT6 How many AI requests may be in flight at once. Higher is faster until the API rate-limits you; 1 restores fully serial behaviour.
TLF_MAX_SLICES400 Max pages read per table (0 = no limit). Lower it to trade coverage for speed.
TLF_FAST_EXTRACT1 Set to 0 to read pages with your chosen model instead of the fast one (slower, and rarely needed — two precision guards already re-check the numbers).
Fresh re-run only re-reads the current edition. Last year's PDF cannot have changed, so its cached reading is kept — that alone removes a large share of the work. If you edit study_config.json's extraction wording and want everything re-read, that is the kind=rebuild run.

8. What each check means

Every finding carries one risk tier from the checklist — just two levels: High a real QC signal (a broken sum, an N that dropped versus last year) and Low worth a look or informational (e.g. an N that grew as data accrued). That single High/Low label is the only severity marker on a finding.

A finding’s check id tells you where it came from: FMT-* / XOUT-* = structural (deterministic Python); AIW-* = within-table AI judge; AIX-* = cross-output AI judge; AIV-* = version (versus prior) AI judge. The number is the checklist item — e.g. AIW-2.1 is item 2.1 below.

Structural — deterministic, no AI (checklist §1)

Item · check idRiskWhat it verifies
1.1 · FMT-010Low Empty or blank pages anywhere in the delivery.
1.2 · XOUT-020Low An output present in the prior edition is missing from the current one.
1.3 · XOUT-001High A gap in output numbering (e.g. Table 4.3 → 4.5 with no 4.4).

Within-table — AI judge (checklist §2 & §7.2)

Item · check idRiskWhat it verifies
2.1 · AIW-2.1High Subgroups under a heading sum to that heading’s N (e.g. fictional studies sum to the corresponding condition-group row).
2.2 · AIW-2.2High Component columns in a row sum to the row’s total (e.g. Monotherapy + Combination = Compound Z All; Compound Z All + Comparator + Blinded = Any Study Drug).
2.3 · AIW-2.3High Numeric integrity within a table: no count exceeds its group N; a percent equals round(n/N×100); AE severity ordering holds (Grade≥3 / Serious / Deaths / Withdrawals ≤ Any AE); a blank total beside present components is flagged as a missing N (FMT-002).
7.2 · AIW-7.2High In an AE-overview table, no treatment-group column is entirely 0 and the “Any Adverse Event” row has no 0.

Cross-output — AI judge (checklist §3–§5, §7.1, §8)

Item · check idRiskWhat it verifies
3 · AIX-3High Each indication’s Table 1 group N’s match its pooled AE-overview and SOC/PT tables. A study deliberately summarized separately (an intended exclusion) is not flagged.
4 · AIX-4High Table 1’s per-study subjects match the by-study tables (intended exclusions not flagged).
5 · AIX-5Low The studies in each indication are listed correctly in the AE-overview table footnotes.
7.1 · AIX-7.1High An AE-overview table’s category totals reconcile with the corresponding SOC/PT table.
8 · AIX-8High By-study tables match explicitly equivalent fictional population rows in Table 1, and expected by-study outputs missing versus the prior edition are flagged.

Versus the prior edition — AI judge (only when two editions are uploaded)

Item · check idRiskWhat it verifies
6.1 · AIV-6.1Low Studies or rows that appear now but were not in the prior edition.
6.2 · AIV-6.2High A group N or subject count that decreased versus the prior edition — counts should only grow as data accrues, so a decrease is a real signal.
6.3 · AIV-6.3Low A group N that increased versus prior (expected as data accrues; informational).
7.3 · AIV-7.3High AE-overview counts versus prior — decreases are High, increases Low.
7.4 · AIV-7.4High In SOC/PT tables, a preferred-term n that decreased or a 0 in the “Any Adverse Event” row; also a preferred term renamed or moved to a different System Organ Class between versions.

Roadmap. Item 9 — cross-document reconciliation (IB vs PSUR/DSUR: the same study under different IDs, indication big-N mismatches) — is defined in the checklist but gated on multi-document upload the app does not yet support, so it does not run.

The full, editable catalogue lives in study_config.json (see §12).

9. Acting on findings

Each finding card offers:

  • Edit & post — turn it into a review comment (you can edit the text first). This marks the output In Progress and the comment is tagged ai in the Comments tab.
  • Reject — dismiss it (the card is struck through).
  • Reopen — undo a previous post/reject.

Click a finding’s output label to jump straight to that table in the TLF workspace and verify it against the PDF. Your post / reject / reopen decisions are logged (with the finding’s context) so the tool can learn from how reviewers act.

10. Asking the AI 💬

  • Global chat (right side of the AI Review tab) — ask about the whole delivery, e.g. “Which tables have an N decrease?” Answers are grounded in the findings and the output list.
  • Per-output chat (TLF sidebar) — scoped to the open table’s extraction and findings.

If you attached a SAP/Protocol, its text is provided to the chat as context. Chat needs an API key.

11. Comments & export 💬

The Comments tab lists every comment (manual and AI-posted) with output, title, text, source and date. Options:

  • Group by output — sort the table by output.
  • ⬇ Export to Excel — download the full comment log as .xlsx for sharing or sign-off.

12. Customising the checklist

The checklist is data, not code. Edit study_config.json in the app folder and re-run. The top-level keys:

  • structural_checks — toggle the three deterministic checks (blank_pages, missing_outputs_vs_prior, numbering_gap).
  • deterministic_checks — the §1 items (1.1–1.3) and the Python check_id that implements each.
  • checklist — the AI-reviewed items (§2–§9). Each has an id, title, risk (High/Medium/Low), scope (within_table / cross_output / version / cross_document), applies_to (which tables it targets), guidance (the rule, in words the AI follows), and examples. Edit the guidance / examples / risk, or add your own item — it takes effect on the next run.
  • selfcheck / verify_pass — the two precision guards (enable/disable and their tolerances).
  • dedupe_findings — collapse duplicate findings.
Examples are guidance, not rules. The examples on each item are few-shot hints shown to the configured model in normal source mode; they are never parsed into hardcoded logic. Plain-language guidance can influence a model response, but it does not guarantee that the check is applied correctly. Results can vary between model runs; the verify pass and self-check can reject some unsupported numeric candidates but cannot establish that a table is correct. The synthetic demo uses pre-seeded results instead.

13. Limitations

  • Reviewer-assist, not auto-approve. Model-backed review can make mistakes, so confirm each finding against the PDF (shown right beside the finding). Treat every finding as a candidate.
  • Results can vary between model-backed runs. The model path is not fixed code, so two runs may not be identical. The extraction self-check and verify pass can reject some misread-number and arithmetic candidates, but do not eliminate model error. The synthetic demo itself is seeded and makes no external model call.
  • Tables only. A run analyses every table in the current edition; listings and figures are not analysed. The tab reports how many were skipped.
  • Version & cross-document. Year-over-year checks need two editions uploaded. Cross-document reconciliation (IB vs PSUR/DSUR, item 9) is on the roadmap and does not run yet.
  • Single user. This public edition has no login, roles, or multi-reviewer separation. PDF inputs only (no RTF conversion), and figures’ image-only content isn’t analysed.
